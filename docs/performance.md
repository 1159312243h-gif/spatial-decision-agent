## 测量协议

运行：

```powershell
python .\scripts\benchmark.py --samples 7 --warmup-runs 2
```

脚本会写入 `evals/results/performance.json`，测量：

- 单候选地/单约束的 GeoPandas 面积、相交与最近距离组合；
- 1,157 条本地 Fixture 上的 POI 分类和半径检索；
- 5 份 Fixture 政策上的 BM25 + 向量 + RRF 检索；
- 24 条冻结评测的完整批次。

每项记录 Python/平台、Fixture 版本、输入规模、预热次数、样本数、中位数、最小值和最大值。结果文件必须由目标机器真实运行生成，不在文档中预填虚构数字。

## 不包含的指标

- 公网高德/Overpass 网络延迟与可用率；
- 真实城市级 POI 数量和覆盖率；
- 大规模 PostGIS 图层的查询计划；
- 多用户并发、任务队列吞吐和 Redis 内存增长；
- LLM Provider 延迟、Token 用量和成本。

这些指标需要真实数据、授权与容量目标后单独设计测试。

## 候选发现延迟预算

候选发现的性能契约分为冷查询和缓存命中，不把公网波动写成固定 SLA：

| 环节 | 默认边界 | 说明 |
|---|---:|---|
| 单次在线尝试 | 15 秒 | 可用性错误每组最多 2 次有界尝试 |
| 重试退避 | 2 到 8 秒 | 指数退避；格式错误不重试 |
| 连续失败阈值 | 12 个批次 | 达到阈值后熔断，避免持续压迫故障 Provider |
| 高德单批分页 | 2 页 | 每页最多 25 条，达到预算时保留截断标记 |
| Provider 请求速率 | 1 次/秒 | 发现与正式分析的并发任务共享线程安全限速器 |
| 高德评分查询 | 6 个业态分组 | 咖啡店和便利店使用相同调度结构、不同 Profile |
| 发现分区补查并发 | 最多 4 个任务 | 6 组 x 4 分区的任务交错进入同一有界执行器 |
| 正式 POI 执行并发 | 最多 4 个任务 | 完整组本地裁剪；不完整组才执行候选局部补查 |
| Redis POI 缓存 | 3600 秒 | 相同空间与类别查询直接复用并标记 `cache_hit` |
| 候选证据快照 | 7200 秒 | 真实完整组本地裁剪；截断、缺失、合成或降级组按候选点补查 |

Workbench 展示 `total_elapsed_ms`、`poi_market_evidence` 节点耗时和缓存命中批次数。冷启动仍受高德/Overpass 网络与配额影响；相同范围的第二次发现应主要由缓存服务，不能用 Fixture 测试耗时代替在线实测。

## 候选发现到正式分析的快照优化

零售 Profile 每个候选有 6 个评分组。原流程在发现后仍为每个候选重新访问 Provider，8 个候选会产生 48 个正式逻辑查询；任一冷请求失败还可能触发熔断和 Fixture 降级，造成发现地图与正式结果证据漂移。

当前流程把发现阶段的 6 个宽域评分组（Provider 支持 bulk 时可更少）冻结为 Redis 快照。正式分析仍生成完整的 48 个查询契约；来源真实、类别齐全且未截断的评分组在内存中按候选、类别、半径和 limit 裁剪并重算指标。宽域结果被截断、缺组、缺类别、使用合成来源或发生在线降级时，才调用后备 Gateway 执行对应候选的正式查询。只有真实 Provider 响应才算补查成功；再次降级到 Fixture 时保留已有快照切片并记录失败，避免用少量合成点覆盖较完整的同批证据。

这项优化减少的是 I/O，不是评分维度。咖啡店和便利店的 `poi_query_limit` 均为 1000；快照完整时保持零重复公网请求，快照达到上限时则用候选点小半径查询纠正边缘覆盖偏差。补查使用原有 Redis 查询缓存，所以相同候选、类别、半径和 Provider 版本可直接命中；首次冷补查仍受 Provider 延迟影响。候选级覆盖表和评分组级 cohort 表同时披露真实/合成、截断、补查失败与最小/最大记录数；只有同组全部候选完整时才允许把数量差异解释为可比较的空间差异。尚未形成在线冷/热请求的统计 Benchmark，不能将本机测试时间写成公网 SLA。

后续性能指标应至少包括 Provider P50/P95、缓存命中率、快照复用率、候选点补查率、补查失败率、fallback 率、单快照字节数、Redis 内存、候选数量与本地裁剪耗时的关系，以及多 Worker 队列等待时间。

## Supervisor 异步边界的性能含义

候选确认现在只执行候选门禁、幂等 Run 创建、RQ 入队和 checkpoint 写入，随后返回 `202 awaiting_analysis`。GIS、POI 快照裁剪、规则、LLM 解释和 DOCX 报告都在 Worker 中执行，因此确认 HTTP 延迟不再等于完整分析时长。`analysis_wait` 是持久 interrupt，不占用 API 请求线程或 Worker。

Workbench 每 2 秒轮询 Supervisor；Worker 完成事件是主恢复路径，GET 做幂等对账和陈旧状态收敛。该设计改善交互延迟和资源占用，不减少实际 GIS/报告计算，也不改善公网 Provider 首次加载速度。本轮相关模块 `69 passed in 3.97s` 只是回归批次耗时，尚未测量确认接口 P50/P95、队列等待、Worker 恢复延迟、GET 对账率或 checkpoint 写放大。

后续应新增：`confirm -> 202` 延迟、`queued -> running` 等待、`Run terminal -> Supervisor terminal` 恢复延迟、回调失败对账次数、transition lock 冲突率、单 session checkpoint 字节数，以及 1/4/8 Worker 下的吞吐与尾延迟。

## 候选发现分区修复的尾延迟控制

发现阶段最多有 6 个不完整评分组，每组固定 4 个分区查询。历史实现按评分组逐批执行，每批 2 Worker；在当时单请求 8 秒超时边界下，六批理论等待接近 96 秒，会穿透 Workbench 的 90 秒默认客户端超时。该 `8 秒 / 2 Worker` 仅用于解释旧故障，不是当前配置。

当前实现将最多 24 个查询合并为一个全局队列，以分区优先、评分组交错的顺序交给最多 4 Worker。真实耗时仍受共享 1 QPS 限速、每次 15 秒超时、最多 2 次尝试、HTTP 建连、Provider 排队、熔断和缓存命中影响；不能用“任务数除以线程数”推导 SLA。查询数量和证据语义没有减少。

Workbench 只把 Supervisor 启动请求的客户端保护线提高到 150 秒，其他 API 仍使用 90 秒默认值。这样可容纳公共 Provider 冷查询的有限尾部延迟，同时避免全局放宽所有操作。需要监控的新增指标包括：补查队列深度、活跃 Worker、每组完成时间、缓存命中率、Provider P95、Supervisor start P95、客户端 504 数量，以及超时后下一次任务的缓存复用比例。

## 正式分析补查与 Run 终态预算

正式分析与发现阶段是两条不同的并发边界。发现阶段最多处理 24 个范围分区任务；正式分析先对所有标准查询尝试快照本地裁剪，只有不完整评分组才产生候选局部联网补查。`execute_poi_queries()` 使用最多 4 个任务并发，并通过 `executor.map` 保留输入输出顺序；Provider 内部仍以全局 1 QPS 启动请求，因此并发用于重叠网络等待，不代表每秒发送 4 个请求。

真实故障样本中，候选发现冻结 7,205 条评分 POI、耗时约 146.62 秒；旧正式路径随后把最多 24 个候选补查串行执行，Run 只有 `created -> enqueued -> started`，超过 14 分钟仍为 `running`。这组数据用于定位故障，不是正常耗时或 SLA。

当前 RQ 任务预算为 180 秒。失败回调是写入 `failed/timed_out` 的第一路径；如果 Worker 被强制终止且回调未能更新 Redis，API 读取会在 `180 + 30` 秒后把仍为 `running` 的 Run 原子收敛为 `timed_out`，错误类型为 `StaleWorkerTimeout`。迟到 Worker 在发布结果前检查外部终态，不能覆盖已经超时或取消的 Run；Supervisor 再通过幂等 GET 对账恢复自己的终态。该机制保证异常任务可解释地结束，不保证公网查询一定在 180 秒内成功。

验证和监控需要分别记录：本地裁剪数量、候选补查数量、补查并发、Provider 实际请求启动速率、重试次数、RQ 任务年龄、`StaleWorkerTimeout` 数量、迟到 Worker 发布拦截、Run 终态到 Supervisor 终态的对账延迟。相关模块回归 `69 passed in 3.97s` 只证明这些状态与顺序契约，不代表线上容量。
