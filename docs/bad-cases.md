# Bad Case 报告

本报告记录系统已经覆盖的失败模式和仍未解决的产品风险。所有复现数据均为合成 Fixture。

## 2. 人工复核边界

规则命中与 POI Fixture 降级会生成警告并要求人工复核。人工操作只有 `pending -> acknowledged`，没有 `approved` 状态。重复确认是幂等的，首次备注保留在审计事件中。

以下表述均被禁止：

- “人工确认后地块合规”
- “未命中规则所以地块合规”
- “软评分最高所以系统推荐该地块”
- “Fixture POI 足以代表真实周边设施”

## 3. 尚未关闭的风险

### Fixture POI 覆盖不足

当前 32 条 POI 只服务于自动化路径，不能支撑城市级密度、竞争度或可达性判断。接入真实数据前需要覆盖率抽样、类别映射准确率、分页完整性、更新频率和成本评估。

### 在线 Provider 不稳定

高德和 Overpass 仍可能发生授权失效、配额耗尽、延迟尖峰、返回结构变化和区域覆盖差异。当前重试/熔断只解决可用性，不保证数据正确性。生产环境应增加 Provider 指标、告警、预算控制和抽检。

### 坐标转换误差

GCJ-02 到 WGS84 的迭代转换适用于工程接入，但不能替代测绘级精度验证。距离阈值敏感场景必须记录转换方法、误差预算并进行控制点抽检。

### 合成政策与规则

当前政策文本、规则阈值和适用范围均为 Fixture。系统只证明规则版本、引用与证据链能被执行，不证明真实政策已覆盖。真实上线需要业务专家审查、有效期管理、行政区继承和变更审批。

### 性能与容量未知

本地性能脚本使用单要素、32 条 POI 和 3 份政策，不代表大图层、并发请求或公网 Provider。需要基于真实数据量做 PostGIS `EXPLAIN ANALYZE`、连接池、Redis 内存、报告生成和并发压力测试。

### 单实例同步运行

当前 `POST /runs` 同步执行工作流，Redis 保存状态但没有独立任务队列。长任务或多实例部署需要任务队列、租约、取消、超时、恢复和幂等状态机。

## 4. 新 Bad Case 进入流程

1. 保存脱敏的最小输入、Fixture 版本和运行环境。
2. 先写失败测试或评测案例，避免只在文档中描述。
3. 明确是输入错误、数据错误、可用性错误还是业务规则缺口。
4. 修复后记录实际输出，不修改期望来迁就实现。
5. 涉及政策、阈值或推荐语义时必须由业务人员复核。
