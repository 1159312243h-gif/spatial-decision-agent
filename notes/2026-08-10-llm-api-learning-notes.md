## 2. Token

### 2.1 Token 是什么

Token 是大模型读取和生成文本时使用的基本计算单位。

模型不会直接把“一个汉字”或“一个英文单词”固定当成一个单位，而是先通过分词器把文本拆成 Token，再把 Token 转换成数字进行计算。同一句话使用不同模型的分词器，得到的 Token 数量可能不同。

例如：

```text
建设项目选址审查
```

这句话可能被拆成多个 Token。一个英文单词可能对应一个 Token，也可能被拆成几个词片段。

### 2.2 Token 会影响什么

Token 主要影响：

1. 上下文容量：一次请求能够容纳多少输入和输出。
2. 调用费用：多数模型按照输入和输出的 Token 数量计费。
3. 响应时间：输入和输出越长，模型通常需要处理更长时间。

一次请求涉及的 Token 可以简化理解为：

```text
总 Token 数
= System 消息
+ 历史 User/Assistant 消息
+ 当前 User 消息
+ 工具返回内容
+ 本次模型输出
```

### 2.3 一句话总结

> Token 是模型处理文本的基本单位，它不完全等于汉字数或英文单词数，并会影响上下文容量、费用和响应速度。

## 3. 上下文与上下文窗口

### 3.1 什么是上下文

上下文是模型在处理当前请求时能够看到的全部信息，可能包括：

- System 提示词；
- 之前的 User 消息；
- 之前的 Assistant 回复；
- 当前 User 问题；
- 工具调用结果；
- 程序额外提供的项目资料。

例如，用户先说：

```text
我要审查一个光伏项目。
```

随后又问：

```text
它是否涉及生态保护红线？
```

模型只有再次看到前面的消息，才知道“它”指的是光伏项目。

### 3.2 模型为什么能进行多轮对话

模型通常不会自动永久记住以前的聊天。程序在下一次调用 API 时，需要把仍然有用的历史消息再次放入 `messages` 中。

因此，多轮对话能力主要来自：

```text
程序保存历史消息
-> 下一次请求重新发送历史消息
-> 模型结合历史消息回答当前问题
```

### 3.3 超过上下文窗口会怎样

不同模型和 API 的行为可能不同：

- 直接返回上下文长度超限错误；
- 自动截断部分内容；
- 由应用程序删除较早的消息；
- 先总结旧消息，再把摘要放入新的上下文。

如果直接删除旧消息，模型可能忘记项目类型、建设规模、候选地块或者输出格式等重要要求。

后续要实现的简单滑动窗口是：

```text
始终保留 System 消息
+ 只保留最近若干轮 User/Assistant 对话
+ 加入用户当前问题
```

### 3.4 一句话总结

> 上下文是模型当前能够看到的信息；上下文窗口容量有限，所以程序必须管理历史消息。

## 4. 消息角色

一个典型的聊天请求可以表示为：

```python
messages = [
    {
        "role": "system",
        "content": "你是一名建设项目选址合规审查助手。",
    },
    {
        "role": "user",
        "content": "请分析一个光伏项目的选址风险。",
    },
    {
        "role": "assistant",
        "content": "建议依次检查生态保护红线、永久基本农田等约束。",
    },
]
```

### 4.1 System

System 消息用于规定模型的身份、任务边界、行为规则和输出要求。

例如：

```text
你是建设项目选址合规审查助手。
只提供前期辅助判断，不替代法定审批结论。
输出必须包含检查步骤和风险提示。
```

System 相当于为模型制定工作规则。

### 4.2 User

User 消息表示用户当前提出的问题、需求或者提供的数据。

例如：

```text
项目类型为光伏发电，请把选址审查任务拆成 5 个步骤。
```

User 告诉模型本次具体需要完成什么。

### 4.3 Assistant

Assistant 消息表示模型之前生成的回复。

在多轮对话中，将以前的 Assistant 消息重新传给模型，可以让模型知道自己之前回答过什么，使后续回答保持连续。

### 4.4 一句话总结

> System 定规则，User 提需求，Assistant 保存模型的历史回复和对话轨迹。

## 5. Temperature

### 5.1 Temperature 是什么

模型生成下一个 Token 时，通常有多个候选结果，每个候选结果都有相应概率。Temperature 用于调整模型在候选结果之间选择时的随机程度。

Temperature 不代表模型的聪明程度。调高 Temperature 不会让模型更准确，只会让输出更加多样和不稳定。

### 5.2 较低的 Temperature

例如：

```python
temperature = 0.1
```

通常具有以下特点：

- 输出相对稳定；
- 更倾向选择高概率内容；
- 多次调用的结果比较接近；
- 适合分类、信息抽取、合规审查和结构化任务拆分。

建设项目选址合规审查需要结果相对稳定、格式明确，可以先使用 `0` 到 `0.3` 的较低值。

### 5.3 较高的 Temperature

例如：

```python
temperature = 0.9
```

通常具有以下特点：

- 输出更加多样；
- 表达更有创造性；
- 多次调用的结果可能明显不同；
- 更容易偏离固定格式或产生不稳定内容。

较高的 Temperature 更适合文案创作、头脑风暴和开放式方案推荐。

### 5.4 一句话总结

> Temperature 控制模型输出的随机程度：低温度更稳定，高温度更多样。

## 6. 四个概念之间的关系

可以用一次选址 Agent 请求来理解：

```text
System：规定模型是选址合规审查助手，并限制职责边界
User：提交项目类型、建设需求和候选地块信息
Assistant：返回检查步骤、风险点和后续建议
Context：保存本次审查需要的指令、数据和历史消息
Token：衡量输入、历史记录和模型输出的长度
Temperature：控制输出结果的稳定程度
```

## 7. 闭卷复述版本

> Token 是模型处理文本的基本单位，决定容量、费用和部分响应时间。
>
> 上下文是当前请求中模型能够看到的全部信息，但上下文窗口长度有限。
>
> System 负责制定规则，User 提出需求，Assistant 表示模型此前的回复。
>
> Temperature 控制生成结果的随机程度，合规审查等稳定任务通常使用较低温度。

### 8.1 原生模型 API 调用

#### Codex 当前会话与开发者 API 的区别

当前 Codex 对话由 Codex 应用负责连接模型。应用不会把内部使用的凭据或会话直接提供给本地 Python 程序，因此项目代码不能直接“复用当前聊天中的模型”。

如果本地 Python 程序需要调用模型服务，需要单独完成以下配置：

1. 登录模型服务的管理平台。
2. 创建或获取开发者 API Key。
3. 确认 API 账户具有调用权限和可用额度。
4. 确认接口协议、Base URL 和实际模型标识。
5. 通过环境变量向程序提供 API Key。

Codex 或其他聊天工具中能够使用某个模型，不代表本地 Python 程序自动拥有相同凭据、权限或额度。

如果继续只在 Codex 对话中提问，虽然仍然能够使用模型协助开发，但不能算作“自己的 Python 程序完成了原生模型 API 调用”。

### 8.2 配置与密钥管理

配置文件放在项目根目录，与 `README.md`、`requirements.txt` 和 `.gitignore` 同级：

```text
ai-agent-learning/
|- .env             # 本机真实配置，禁止提交
|- .env.example     # 配置示例，可以提交
|- .gitignore
|- requirements.txt
|- practice/
`- app/
```

`.env` 保存本机使用的真实值：

```dotenv
LLM_API_KEY=这里填写新生成的真实密钥
LLM_BASE_URL=这里填写公司接口地址
LLM_MODEL=这里填写接口实际使用的模型标识
```

`.env.example` 只展示变量名称和占位内容：

```dotenv
LLM_API_KEY=replace-with-your-api-key
LLM_BASE_URL=https://replace-with-your-api-base-url/v1
LLM_MODEL=replace-with-an-available-model
```

以上内容应写入对应文件，不能作为 PowerShell 命令直接执行。

当前 `.gitignore` 已包含：

```gitignore
.env
```

安全检查原则：

- `.env` 不执行 `git add -f`。
- `.env.example` 中不得出现真实 Key。
- 提交前使用 `git status --short`，确认看不到 `.env`。
- 使用 `git diff --cached`，检查暂存区中没有密钥。
- 如果真实 Key 曾经提交到 Git，应立即在模型平台撤销并重新创建，不能只删除文件。

### 8.3 上下文滑动窗口

- 使用 `ConversationContext` 管理历史消息。
- 使用 `deque(maxlen=max_rounds)` 以完整对话轮次为单位保存历史。
- 一轮对话由一条 User 消息和对应的一条 Assistant 回复组成。
- 本次演示窗口保留最近 2 轮对话。
- System 消息不进入滑动窗口，而是在每次 API 调用时通过 `instructions` 单独传入，因此不会随旧历史一起删除。
- 超过窗口后自动删除最早的一轮 User/Assistant 消息。

本地逻辑测试：

1. 依次加入“问题1/回答1”“问题2/回答2”“问题3/回答3”。
2. 因窗口上限为 2，构造下一次输入时只包含问题2、回答2、问题3、回答3和当前问题4。
3. 测试证明最早一轮已经被自动移除。

真实 API 测试：

1. 第一轮要求模型记住候选地块编号 `A01`。
2. 第二轮询问刚才提供的候选地块编号。
3. 模型正确回答 `A01`，证明程序把第一轮消息重新发送给了模型。
4. 该能力来自应用程序管理并重发上下文，不代表模型永久记住了用户信息。

### 8.4 选址任务拆分

- 输入的建设项目需求：建设一个占地 30 公顷的物流园，对两个候选地块进行比较，检查交通条件、生态保护红线、永久基本农田和城镇开发边界。
- 模型输出了 5 个有顺序的执行步骤：
  1. 收集并核实基础资料；
  2. 开展交通条件调查与比较；
  3. 叠加核查国土空间规划管控边界；
  4. 核对相关管控规则及项目适配性；
  5. 形成候选地块对比与报审材料清单。
- 输出具有明确先后顺序，先准备数据，再开展空间与交通分析，之后核对规则并形成成果。
- 对缺少的坐标、权属、现状用途、交通流量、数据版本和政策适用信息明确标记为需要补充或核实。
- 输出没有编造候选地块已经合规，也没有代替主管部门作出最终审批结论，符合项目辅助审查边界。
